# WHO-S5：Desktop / Mobile 接线、确认 UI、与现有邮件中心关系

状态：**待启动 · 依赖 S2–S4**

负责人：待指派

执行仓库：`uichat-mira/who-you`（服务端契约）+ `mira-desktop` / `mira-mobile`（客户端接线，需各自合同）

设计依据：[`docs/product-design.md`](../product-design.md) v1 §1、§7.3、§12。

## 背景

Who You 最终必须对用户可见：用户在 Mira 客户端里看到 `@tomlab.cn` 邮箱、读邮件、起草、**对具体草稿确认发送**。S5 只做接线与体验，不改变 S1–S4 已定的服务端契约。

现有 Mira Desktop 邮件中心是 IMAP/SMTP 多账号路径，与本设计不是同一条数据路径。S5 必须明确：长期并存、逐步迁移，还是由 Who You 取代；未裁决前不得改动现有邮件中心行为。

## Goal

1. 客户端可展示 Who You 地址、收件箱、线程、正文与附件。
2. 草稿编辑与确认 UI 完整：用户看到最终形态后才能产生确认凭证。
3. 错误态可理解：隔离、配额、限流、发送失败、退信。
4. 完成一次真实端到端旅程：查看草稿 → 确认 → 发送 → 看到回执。

## In Scope

- Desktop / Mobile 产品合同（各仓独立 Issue / PR）。
- 确认 UI 与客户端侧凭证获取（对接 S2 的 A / B 方案）。
- 邮箱入口、列表、线程、正文、附件、草稿编辑、发送状态。
- 错误态与失败恢复。
- 与现有桌面邮件中心关系的裁决与实施边界。

## Out of Scope

- 服务端新增业务能力（回到 S1–S4 合同）。
- 第三方 MCP 客户端。
- 富文本编辑器、联系人、日历、规则引擎。
- 邮件迁移工具（若需要迁移，另开卡）。

## 验收证据

1. 用户在 Desktop 或 Mobile 完成「查看草稿 → 确认 → 发送 → 回执」一次真实旅程。
2. 未确认时无发送入口可绕过；确认后改稿需重新确认。
3. 隔离邮件、配额超限、relay 失败均有明确用户可见状态。
4. 现有桌面邮件中心行为未被无授权改动（回归证据）。
5. 客户端日志与埋点不含地址、主题、正文、附件名。

## 依赖与阻塞

- S2 的确认契约已定稿；S4 的错误码稳定。
- Desktop / Mobile 各自产品与安全合同。
- 现有桌面邮件中心关系的维护者裁决（v1 §11 #11）。

## 待决

1. 首版只做 Desktop 还是 Desktop + Mobile 同步。
2. 确认凭证在客户端的持有与传递方式（与 S2 方案一致）。
3. 离线缓存是否落地本地、如何加密。
4. 是否保留旧邮件中心作为并存入口。
